# Обновления мобильного приложения

APK раздаётся с сайта и из S3, не через Google Play. Из этого следуют две вещи:
пользователь может месяцами сидеть на старой сборке, а сломанный релиз нельзя
«отозвать» — он уже установлен. Поэтому у приложения есть реестр сборок и политика
обновлений: сервер говорит каждому клиенту, есть ли версия новее и обязательно ли
обновиться.

## Модель

Таблица `app_versions` (миграция `000011`), одна строка = одна сборка платформы:

| поле | смысл |
|---|---|
| `platform` | `android` (сейчас) / `ios` (на будущее) |
| `version_code` | `BuildConfig.VERSION_CODE` = число коммитов в HEAD; **растёт с каждым коммитом** |
| `version_name` | `0.1.0+<sha>` — то, что видит пользователь |
| `download_url` | публичная ссылка APK (сейчас `https://s3.inceptech.ru/coffeely/coffeely.apk`) |
| `sha256` | контрольная сумма файла, клиент сверяет её перед установкой |
| `size_bytes` | размер для попапа «12 МБ» |
| `mandatory` | **блокирующая сборка**: всем, кто ниже, вход закрыт |
| `changelog` | «что нового» в попапе (CI пишет тему коммита) |

Правило сервера:

- `latest_version_code` = максимальный `version_code` платформы;
- `min_supported_version_code` = максимальный `version_code` среди `mandatory`;
- `update_available` = клиент < latest → мягкий попап;
- `update_required` = клиент < min_supported → непроходимый экран.

Блокировка не привязана к «текущей последней» сборке: если версия 52 помечена
`mandatory`, то 51 и всё ниже закрыты, а 53 без флага — просто мягкое обновление.
Снять блокировку можно в любой момент, не трогая APK.

## API

### Проверка — публичная

`GET /app/version?platform=android&version_code=51`

```json
{
  "platform": "android",
  "client_version_code": 51,
  "update_available": true,
  "update_required": true,
  "latest_version_code": 52,
  "latest_version_name": "0.1.0+a1b2c3d",
  "min_supported_version_code": 52,
  "download_url": "https://s3.inceptech.ru/coffeely/coffeely.apk",
  "sha256": "…64 hex…",
  "size_bytes": 13070849,
  "changelog": "исправлена выдача окон"
}
```

Эндпоинт **без аутентификации**: проверка нужна до входа. Иначе гость со старой
сборкой упрётся в сломанный логин и решит, что «сервер упал», вместо «обновитесь».
`version_code` обязателен, `platform` — обязателен (`android`/`ios`), мусор → 400.

Пустой реестр — не ошибка: `update_available=false`, `update_required=false`.
Сервер никогда не блокирует приложение только потому, что в реестре пусто.

### Публикация и блокировка — по секрету админки

Оба эндпоинта под `X-Admin-Secret` (тот же `ADMIN_CRM_SECRET`, что у внутренней
админки; лимитер 20 попыток / 15 мин на IP).

`POST /internal/admin/app-versions` — регистрация/обновление сборки (upsert):

```sh
curl -X POST https://coffeely.inceptech.ru/api/internal/admin/app-versions \
  -H "X-Admin-Secret: $ADMIN_CRM_SECRET" -H 'Content-Type: application/json' \
  -d '{"platform":"android","version_code":52,"version_name":"0.1.0+a1b2c3d",
       "download_url":"https://s3.inceptech.ru/coffeely/coffeely.apk",
       "sha256":"<64 hex>","size_bytes":13070849,
       "mandatory":true,"changelog":"исправлена выдача окон"}'
```

`PATCH /internal/admin/app-versions/{platform}/{version_code}` — включить/снять
блокировку у уже выпущенной сборки (аварийный рычаг):

```sh
curl -X PATCH https://coffeely.inceptech.ru/api/internal/admin/app-versions/android/52 \
  -H "X-Admin-Secret: $ADMIN_CRM_SECRET" -H 'Content-Type: application/json' \
  -d '{"mandatory":false}'
```

Проверка после изменения:

```sh
curl "https://coffeely.inceptech.ru/api/app/version?platform=android&version_code=51" | jq
```

## Как выходит релиз

1. Пуш в `main` → CI собирает release-APK, проверяет подпись и `versionCode`,
   кладёт `coffeely.apk` и `builds/coffeely-<sha>.apk` в S3.
2. Тот же job вызывает `POST /internal/admin/app-versions`: `version_code` и
   `version_name` берутся из APK (`aapt2 badging`), `sha256` и размер — из файла,
   `changelog` — тема коммита.
3. Флаг `mandatory` CI берёт из **трейлера сообщения коммита**:

   ```
   feat(mobile): новый экран заказа

   Force-Update: true
   ```

   Есть трейлер → сборка блокирующая. Нет → обычное мягкое обновление.
4. Если `ADMIN_CRM_SECRET` в GitHub не задан или backend ещё не знает эндпоинт —
   шаг пишет warning и не валит релиз: APK в S3 уже лежит, его качают с лендинга.

CI не деплоит backend. Порядок для первого выката фичи: задеплоить backend
(миграция `000011` + рестарт) → добавить секрет `ADMIN_CRM_SECRET` в GitHub →
следующий APK сам зарегистрируется. До этого реестр пуст, и приложение ведёт
себя как раньше.

## Поведение приложения (Android)

- При старте и дальше раз в 15 минут — `GET /app/version` со своим `versionCode`.
- **Блокирующая версия** (`update_required`): полноэкранный экран вместо
  приложения — ни логина, ни заказов. Скачивание начинается сразу, кнопки:
  «Установить», «Скачать в браузере», «Закрыть приложение». Кнопки «Позже» нет.
- **Обычное обновление** (`update_available`): попап «Доступна новая версия» с
  версией, changelog и размером. «Обновить» → прогресс и инструкция; «Позже»
  скрывает попап до перезапуска (или до следующей новой версии). Вернуться к
  обновлению можно из «О программе» — там же версия сборки и «Проверить обновления».
- **Нет сети / сервер недоступен**: приложение работает, блокировка не
  включается. Но последняя полученная политика сохраняется на устройстве:
  если сервер уже сказал «обновитесь», перезапуск без интернета этого не отменит.
- Сборка впереди реестра (локальная, бета) — сервер её не трогает.

### Скачивание и установка

- Файл качает `DownloadManager` в приватный каталог приложения: прогресс в
  шторке, загрузка не прерывается при закрытии попапа. «Скрыть» не отменяет
  скачивание.
- После загрузки клиент сверяет **SHA-256** с серверным. Не совпало — файл
  удаляется, показывается «файл повреждён, скачайте ещё раз». Подменённый APK
  установить нельзя.
- Установщику файл отдаётся через `FileProvider` (`${applicationId}.updates`),
  разрешение `REQUEST_INSTALL_PACKAGES` объявлено в манифесте.
- Первый раз Android требует разрешение «Устанавливать неизвестные приложения»
  для coffeely. Клиент открывает нужный экран настроек, а файл **сохраняет**:
  после разрешения достаточно нажать «Установить» — качать заново не нужно.
- Подпись одна и та же (`coffeely`, SHA-256 `66:2E:…:8C:70`), поэтому обновление
  ставится поверх без удаления и потери данных.

### Что видит пользователь во время скачивания

Короткая инструкция из четырёх шагов (дословно в `UpdateScreens.kt`):

1. дождаться конца загрузки (прогресс есть и в шторке);
2. в установщике нажать «Обновить»/«Установить»;
3. разрешить установку из этого источника — это стандартный вопрос Android,
   потому что приложение ставится не из Google Play;
4. если Play Protect предложит проверку — согласиться; при «Всё равно
   установить» — подтвердить.

Плюс прямая формулировка, почему это безопасно: приложение подписано нашим
ключом, контрольная сумма сверена с сервером, подменённый файл не установится.
Это правда, а не успокаивающая фраза: проверка Play Protect для нашего APK
безвредна, а целостность файла проверяется до запуска установщика.

## Когда помечать релиз блокирующим

Блокировка — это «пользователь не может войти, пока не обновится». Поэтому:

- **да**: сломана совместимость с API (старый клиент шлёт не то и портит
  заказы/время), критичная уязвимость, ошибка, из-за которой бариста не видит
  заказы, обязательная миграция схемы;
- **нет**: новые фичи, косметика, улучшения — это мягкое обновление;
- нельзя блокировать сборкой, которая сама не проверена: заблокированные
  пользователи уйдут ставить именно её.

Аварийный сценарий «блокирующая сборка оказалась плохой»:

1. выпустить исправление с большим `versionCode` и `mandatory=true` — оно
   перекроет плохую блокирующую версию;
2. если исправления нет — `PATCH ... {"mandatory":false}` на плохой версии:
   вход откроется, обновление останется мягким;
3. если сломан и сам APK в S3 — вернуть в бакет предыдущий
   `builds/coffeely-<sha>.apk` и поправить `download_url`/`sha256` через `POST`
   с тем же `version_code` (upsert перезапишет запись).

## Ограничения и что дальше

- **Клиентская проверка, а не серверная.** Старый клиент можно остановить только
  на экране; API по-прежнему ответит клиенту, который дошёл до запроса (например,
  через прокси). Это осознанно: серверный 426 на все запросы при ошибке в
  `mandatory` запирает вообще всех, включая тех, кто уже обновился. Если
  понадобится — добавляется middleware по заголовку `X-App-Version-Code` и
  возврат 426; клиентская часть уже готова.
- **iOS.** API платформо-независим: `platform=ios` + `download_url` на App Store.
  Принудительное обновление там ограничено политикой Apple (пользователь может
  не обновляться), поэтому «блокирующий» экран на iOS — это предупреждение плюс
  ссылка в App Store. Делать это вместе с первым iOS-релизом.
- **Google Play.** Если приложение когда-нибудь пойдёт в Play, механизм остаётся
  (проверка версии + экран), но скачивание заменится на Play-ссылку, а
  `REQUEST_INSTALL_PACKAGES` из манифеста уйдёт — политика Play его не любит.
- **Бета-каналы.** Реестр — один на платформу; отдельного канала «бета для
  нескольких телефонов» нет. Локальные сборки с большим `versionCode` просто
  не считаются устаревшими.
