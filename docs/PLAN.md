# PLAN.md — вехи разработки coffeely

Статус: обновлён 2026-11-15 после создания репозитория.
Источник требований: YouGile `ai-knowlege` (AIK-11, AIK-14, AIK-13, AIK-15).

## Принципы

- Работаем вехами, не по часам. Код пишет агент; пользователь — решения и приёмка.
- Каждая веха заканчивается: зелёной сборкой, коммитом(-ами) в `main`, обновлением
  статуса в этом файле и, если принято бизнес-решение, — записью в `ai-knowlege`.
- Пороговые метрики из AIK-14 §6 (дедлайны, повторные заказы, промахи) должны
  собираться системой с первой версии — это данные для проверки гипотезы.

## M1 — Dev-окружение и схема БД (ЗАКРЫТА 2026-11-15)

**Цель:** поднимаемый одной командой dev-стек и первая версия схемы, на которой
строятся M2–M4.

Задачи:
1. `deploy/dev/docker-compose.yml`: postgres:17 (том, healthcheck), и nothing else.
   Переменные — в `deploy/dev/.env.example`, реальный `.env` в `.gitignore`.
2. Миграции `backend/migrations/` (golang-migrate, SQL, up/down). Схема v1:
   - `users` (id uuid, role enum client/barista/owner, email citext unique, password_hash,
     yandex_id, created_at) — role owner резервируем под будущий CRM-сайт;
   - `points` (id, title, address, geo, timezone, capacity_config jsonb — слоты/окна/лимиты,
     is_active);
   - `barista_points` (user_id ↔ point_id, многие-к-одному: один бариста — одна точка) 
     + `barista_invite_codes` (code unique, point_id, created_by, used_by, expires_at);
   - `menu_items` (point_id, title, price_minor, prep_seconds, is_available);
   - `orders` (id, point_id, client_id, status enum created/paid/in_production/ready/
     given_out/cancelled, pickup_slot_start, pickup_slot_end, deadline_at, total_minor,
     payment_ref, created_at) — `deadline_at` вычисляется движком, это ядро AIK-11;
   - `order_items` (order_id, menu_item_id, qty, price_minor);
   - `order_events` (order_id, event, at, actor_id) — журнал статусов, из него считаются
     метрики % дедлайнов и промахов (AIK-14 §6).
3. `backend/internal/config` — конфиг из env (PORT, DATABASE_URL), загрузка в main.
4. Подключение БД: `pgx`/`pgxpool`, graceful shutdown, `readyz` начинает проверять БД.
5. Makefile в `backend/`: `make dev-up`, `make migrate`, `make build`, `make test`.

**Приёмка (выполнено 2026-11-15):** `make dev-up && make migrate && make run` —
`readyz` отвечает `{"status":"ready","db":true}`; миграции подняты с нуля, откат и
повторный подъём проверены; схема в коммите. Примечание: docker 29 требует
отдельного пакета `docker-compose` (compose-плагин), на машине установлен.

## M2 — Аутентификация и роли (ЗАКРЫТА 2026-11-15)

1. Регистрация/вход по email+пароль: argon2id (RFC 9106, 64 MiB), JWT access (15 мин,
   HS256 + jti) + refresh (30 дней, ротация, в БД только SHA-256 хеш; повторное
   использование отозванного токена отзывает все токены пользователя).
2. Yandex ID: `/auth/yandex/start` → `/auth/yandex/callback`, связка по email
   (вход по yandex_id / привязка к email / регистрация). URLs конфигурируемые —
   тесты гоняются против mock-OIDC.
3. Роли: middleware `Authenticate` + `RequireRole`; бариста привязывается к точке
   через `POST /barista/claim-invite` (клиент → бариста атомарно, в транзакции).
4. Коды приглашений: выпуск только owner (`POST /admin/invite-codes`, владелец
   сеется в БД до M7), одноразовость на уровне UPDATE ... WHERE used_by IS NULL,
   TTL (дефолт 7 дней), читаемый Crockford base32.

**Приёмка (выполнено 2026-11-15):** e2e-тесты в `internal/server/e2e_test.go` —
регистрация/вход/refresh+ротация/re-use/выход, Yandex ID на mock-OIDC, claim-invite
(успех, повтор, чужой код, протухший код), 401/403 на чужих ролях. Всё зелёное
против живого Postgres (`coffeely_test`). Smoke-тест на dev-сервере пройден.

## M3 — Бариста-KDS (вход в производство) (ЗАКРЫТА 2026-11-15)

**Ядро продукта: без этого ничего не работает (AIK-11 §4).**

1. API: очередь заказов точки (live), статусы `in_production` / `ready` / `given_out`,
   фикс промаха дедлайна.
2. Realtime v1: WebSocket-канал на точку (позже Centrifugo) — новые заказы и статусы
   толкаются баристе без поллинга.
3. Дедлайны: `deadline_at` = время окна выдачи минус prep_seconds напитков; движок
   считает и отдаёт баристе «№412 — к 8:41, делать сейчас».
4. Метрики: % дедлайнов, соблюдённых вовремя, по точке и по дню.

**Приёмка (выполнено 2026-11-15):** e2e — заказ появляется в очереди в realtime
(WebSocket, `TestRealtimeE2E`), бариста меняет статус, гость видит изменение
вторым API-клиентом (`GET /orders/{id}`), метрика пишется (`TestDeadlineMissE2E`:
промах → missed=1, % пересчитан). Движок дедлайна проверен на точных значениях
(`TestOrderAndQueueE2E`: окно − max prep_seconds).

Реализация: `internal/orders` (store: create/queue/transition/metrics; handlers;
Hub — подписки на точку, `GET /ws/points/{id}`). Создание заказа v1 — статус `paid`
(«оплата в кассе при получении»), проверка ёмкости окна — M4. Сквозные номера
заказов — миграция 000003 (`order_number`).

## M4 — Клиентский флоу (ЗАКРЫТА 2026-11-15; v2 переработал выбор окон — см. M8)

1. Список точек (geo), меню точки, окна выдачи на сегодня со свободной ёмкостью
   (движок v1: лимит заказов на 5-минутное окно из `capacity_config`).
2. Создание заказа: выбор окна → проверка ёмкости → заказ → статус для клиента
   с точным временем готовности (не «7–10 минут»).
3. Оплата: v1 «оплата в кассе» (пилот); онлайн-оплата (ЮKassa) — M6.

**Приёмка (выполнено 2026-11-15):** e2e — клиент видит окна (`TestClientFlowE2E`),
берёт окно, второй клиент на то же окно получает отказ 409 `window_full`
при исчерпании лимита; конфиг с лимитом 1 и дефолтный (3) проверены отдельно;
заказ виден баристе точки. Гонка на последнее место закрыта `pg_advisory_xact_lock`
на (точка, окно), проверка ёмкости — до вставки заказа в его транзакции.

Реализация: `internal/points` (List/Menu/Windows + CheckWindowCapacity);
таймзона точки учитывается, `time/tzdata` вшит в бинарник. Дефолты соло-режима
(AIK-13): окно 5 мин, лимит 3, работа 08:00–20:00; битый capacity_config = дефолт.

## M8 — Клиентский флоу v2, прод-деплой, лендинг (2026-11-15)

**Запрос пользователя:** «нет кнопки „мои заказы“; клиент должен видеть, что заказ
взяли в работу и ко скольки он будет готов. Люди не должны выбирать окошки — нажав
на кофейню, человек видит примерное время готовки и обновление статусов».

Сделано:

1. **Отказ от выбора окон.** `POST /orders` принимает только `{point_id, items}`.
   Окно назначает движок `points.PlanSlot`: готовность = сейчас + очередь точки +
   prep заказа, округлённая вверх по сетке окон; берётся первое окно со свободной
   ёмкостью, но не раньше готовности (бариста получает полный prep до начала окна).
   `deadline_at = начало окна − prep`. Дальше 120 минут от «сейчас» — `409 point_busy`.
   `GET /points/{id}/windows` удалён: клиент окошек не видит.
2. **Загрузка точки в списке.** `GET /points` отдаёт `load`: `wait_seconds` (сумма prep
   активных заказов), `active_orders`, `is_open`, `opens_at`. Экран кофейни показывает
   «свободно» / «сейчас в очереди 2 — ваш кофе примерно через 5 мин».
3. **«Мои заказы».** `GET /orders` — активные сверху, затем история; в карточке
   название точки, статус, время готовности, сумма. Статус заказа обновляется
   realtime: `GET /ws/orders` (канал пользователя) + страховочный поллинг.
4. **Сессия сохраняется** на устройстве (SharedPreferences + refresh): при повторном
   запуске гость сразу видит свои заказы.
5. **Логирование запросов** в stdout: middleware `httpx.LogRequests` — method, path,
   status, bytes, duration_ms, remote, user_agent, request_id; 4xx=WARN, 5xx=ERROR.
6. **Лендинг** `landing/` (Vite + React → nginx) на `coffeely.inceptech.ru` с раздачей
   APK из S3 (`s3.inceptech.ru/coffeely/coffeely.apk`).
7. **CI** `.github/workflows/ci.yml`: тесты бэкенда против Postgres-сервиса, Docker-образы
   `coffeely-backend:backend` и `coffeely-landing:front` в Docker Hub, сборка APK
   (прод-адрес API) и выкладка в S3. ArgoCD (Incept10n/inceptech, `apps/coffeely`)
   тянет мутабельные теги с `imagePullPolicy: Always`.
8. **Прод-манифесты**: namespace, Postgres (statefulset + PVC), миграции в initContainer
   (`migrate up` теперь идемпотентен — `ErrNoChange` = успех), секреты из OpenBao
   (`secret/coffeely`), nginx-LB: сертификат на `coffeely.inceptech.ru`, API и WebSocket
   под `/api` (префикс срезается), апгрейд для `/api/ws/*`.

Приёмка: e2e-тесты (`TestClientFlowE2E`, `TestWindowCapacityE2E`, M3-набор) зелёные;
apk проверен на эмуляторе — список точек с ожиданием, заказ без окон, точное время,
live-смена статуса баристой, «мои заказы», сохранение сессии после перезапуска.

## M9 — KDS-борда баристы: цвета, категории по статусам (ЗАКРЫТА 2026-11-16)

**Запрос пользователя (2026-11-16):** «у баристы будут светиться разным цветом
и перемещаться по разным категориям товары по статусам, чтобы он всегда понимал,
на что ответил, на что нет, какой заказ новый, какой нет» (записано в AIK-18).

Сделано:

1. **Категории по статусам** (`BaristaScreen`): одна борда с секциями
   новые (`paid`) → в работе (`in_production`) → готово (`ready`) → архив дня
   (`given_out`/`cancelled`). Смена статуса = перемещение карточки
   (`Modifier.animateItem`), 409 `bad_transition` не ломает UI (ошибка + refresh).
2. **Цвета карточек:** новый/неотвеченный — красная рамка с пульсацией
   (дышащая альфа, видно с первого взгляда), в работе — янтарная, готов — зелёная,
   архив — приглушённая серая без кнопок; срочность дедлайна — отдельной меткой
   («делать сейчас», «ПРОМАХ ДЕДЛАЙНА»); тикер раз в 10 с обновляет срочность
   без новых событий.
3. **«Новый» до первого ответа** — решение вехи: отдельное ack-поле на бэкенде
   **не нужно**. Первый ответ баристы всегда смена статуса (взял в работу /
   отменил, переходы валидируются на бэкенде), поэтому признак «нет ответа» —
   это статус `paid`; он синхронен между телефонами и перезапусками приложения
   без локального состояния. Отмена — с диалогом подтверждения.
4. **Архив дня на бэкенде:** `GET /barista/queue` теперь отдаёт и выданные/
   отменённые заказы точки за сегодня (таймзона точки, по событию смены статуса
   из `order_events`, лимит 20, состав заказа включён) — новые/неотвеченные были
   недоступны баристе раньше; срочность у закрытых пустая (`Store.HistoryOfPoint`).
5. **Realtime остаётся:** WS-канал точки + страховочный поллинг.

Приёмка (выполнено 2026-11-16): `go test ./...` зелёный, новый e2e
`TestKDSBoardE2E` (активные + архив дня + состав). На эмуляторе пройден полный
цикл: заказ появляется красным пульсирующим в «НОВЫЕ · НЕТ ОТВЕТА» по WS →
«Взять в работу» → янтарный «В РАБОТЕ» → «Готов» → зелёный «ГОТОВО · К ВЫДАЧЕ»
с меткой «ПРОМАХ ДЕДЛАЙНА» по тикеру → «Выдан» → приглушённый «АРХИВ ЗА ДЕНЬ»;
отмена через диалог подтверждения → «отменён» в архиве.

## M11 — Проверка обновлений и блокирующие версии (РЕАЛИЗОВАНО 2026-11-22)

**Проблема:** APK раздаётся не через Google Play, а с сайта. Пользователь может
сидеть на старой сборке, а сломанный релиз нельзя отозвать — он уже установлен и
ломает заказы.

Задачи:
1. Реестр сборок `app_versions` (миграция `000011`): версия, ссылка на APK,
   SHA-256, размер, changelog, флаг `mandatory`.
2. Публичный `GET /app/version?platform=android&version_code=N` — проверка до
   входа (иначе старый клиент упрётся в сломанный логин и не узнает про обновление).
3. Регистрация сборки из CI (`POST /internal/admin/app-versions` под
   `ADMIN_CRM_SECRET`) + аварийная блокировка/разблокировка уже выпущенной
   версии (`PATCH .../{platform}/{version_code}`).
4. Клиент: проверка при старте и раз в 15 минут; мягкий попап с «Позже» и
   непроходимый экран для блокирующей версии; офлайн-политика из кэша.
5. Скачивание через `DownloadManager` со сверкой SHA-256 и установка через
   `FileProvider`; в процессе — инструкция «Обновить → разрешить установку →
   Play Protect проверить безопасно», файл после разрешения не теряется.
6. «О программе»: версия/сборка, «Проверить обновления», возврат к попапу.

**Приёмка (выполнено 2026-11-22):** `go vet ./...` и `TestAppVersionE2E`
(публикация, мягкое/блокирующее обновление, снятие блокировки, 400/401/404)
зелёные; на эмуляторе пройдено: мягкий попап → «Обновить» → скачивание →
сверка SHA-256 → разрешение установки → системный установщик → «App installed»;
«Позже»; «О программе» → «Обновить до …»; блокирующий экран после
`mandatory=true`, в том числе после перезапуска без доступного backend.
